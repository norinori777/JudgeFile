# JudgeFile Constitution

## 0. 前提

この開発に関するfeature spec、設計文書、運用文書、レビュー記録は、
原則として日本語を用いる。Spec Kit のテンプレートも日本語で維持しなければ
ならない。

## 1. 目的

JudgeFile は、ファイルの中身を解析し、分類・タグ付け・振り分けを支援する。
本プロジェクトは、AI を補助判断に使い、最終的な処理は検証可能で再現性のある形で実行する。

## 2. 基本原則

1. 決定的な処理を優先する
   - ファイル監視、拡張子判定、テキスト抽出、移動処理は可能な限り決定的に実装する。
   - AI は分類補助と要約補助に限定する。

2. 構造化出力を必須にする
   - AI の出力は自由文ではなく、JSON などの構造化形式を基本とする。
   - スキーマ検証に通らない出力は採用しない。

3. 低信頼度の自動実行を避ける
   - 分類結果の信頼度が低い場合は自動移動しない。
   - 不確実な結果は review フォルダまたは人間確認に回す。

4. 抽出と分類を分離する
   - OCR、PDF 抽出、Office 抽出などの前処理と、AI 分類は別責務にする。
   - AI は抽出後のテキストを受け取る。

5. 監査可能性を確保する
   - どのファイルに対して、どの入力を送り、どの判定が返り、どう処理したかを記録する。
   - 後から結果を追跡できることを必須とする。

6. 小さく始めて拡張する
   - 最初の対象は txt, md などの単純なテキスト形式とする。
   - PDF、画像 OCR、Office 文書は段階的に追加する。
   - LangChain は必要性が明確になってから導入する。

## 3. 技術方針

1. 実装言語は Node.js と TypeScript を基本とする。
2. AI 連携は OpenAI SDK を基本とする。
3. フォルダ監視、キュー、ログ、分類、振り分けは独立したモジュールに分ける。
4. 依存ライブラリは最小限に抑え、役割が重複する抽象は増やしすぎない。

## 4. AI 利用ルール

1. ファイル本文は必要最小限だけ送る。
2. 機密情報や個人情報は送信前に除外またはマスキングする。
3. プロンプトは短く、分類基準は固定する。
4. AI の結果はルールとスキーマで検証してから採用する。
5. AI は保存先の最終決定者ではなく、候補提示者として扱う。

## 5. 品質基準

1. すべての分類結果は再現可能であること。
2. 失敗時に処理が中断し、誤った振り分けをしないこと。
3. 処理ログから原因を追跡できること。
4. 自動化率よりも誤振り分けの少なさを優先すること。
5. 新しいファイル形式追加は既存処理を壊さず拡張できること。

## 6. 変更原則

1. 仕様変更はタグ体系、分類基準、保存先ルールを明示して行う。
2. プロンプト変更は出力スキーマとセットで見直す。
3. 振り分けロジック変更は必ず review ルートを保持する。
4. 例外処理を省略せず、失敗時の挙動を先に決める。

## 7. 非目的

1. 完全自動での無確認移動を最優先にはしない。
2. LangChain の採用自体を目的にしない。
3. AI での自由な文章生成を主用途にしない。
4. 大規模な汎用文書管理システムには最初からしない。

## 8. 実装判断の優先順位

1. 正確性
2. 監査可能性
3. 保守性
4. 拡張性
5. 自動化率
