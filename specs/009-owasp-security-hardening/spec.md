# Feature Specification: OWASPセキュリティ強化

**Feature Branch**: `009-owasp-security-hardening`

**Created**: 2026-06-01

**Status**: Draft

**Input**: User description: "PreDesign.mdの4. セキュリティ（OWASP 観点）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ファイルパストラバーサル防止 (Priority: P1)

悪意あるファイルパスや設定値（`../../../etc/passwd` 等）が入力されたとき、システムは監視フォルダ外への読み書き・移動を一切行わない。ファイル処理担当者（オペレーター）は、誤ったルート設定や攻撃的なパスが指定されても、安全に処理が中断されることを確認できる。

**Why this priority**: ファイルパストラバーサルはOWASP Top 10の「安全でないデザイン」に該当し、システム上の任意ファイルへのアクセス・改ざん・流出につながる最も深刻なリスクの一つ。

**Independent Test**: 監視フォルダの外を指す振り分け先ルートや、`../` を含む移動先パスが設定に含まれている状態でファイルを処理させ、システムがエラーを返してファイルを移動しないことを確認できる。

**Acceptance Scenarios**:

1. **Given** 振り分け先に `watchDir` の外を指すパス（例：`../../secret`）が設定されている、**When** ファイルが処理・振り分けされる、**Then** システムはエラーログを出力してファイルの移動を中断し、`watchDir` 外へのファイル操作は一切行われない
2. **Given** 正規の振り分け先パスが設定されている、**When** ファイルが処理・振り分けされる、**Then** 通常通りファイルが正しいフォルダへ移動される
3. **Given** パス設定に `null` バイトや制御文字が混入している、**When** システムが起動または処理を実行する、**Then** バリデーションエラーとして拒否されログに記録される

---

### User Story 2 - 全ファイルタイプへのサイズ制限 (Priority: P1)

テキスト・Markdown・PDF・Officeなど全ファイルタイプに対してサイズ上限が設けられており、巨大ファイルの投入によってシステムが過負荷（DoS）状態になることを防ぐ。オペレーターは、上限を超えたファイルが処理スキップ・レビュー送りになることを確認できる。

**Why this priority**: サイズ上限なしのファイル受け入れはメモリ枯渇・API超過課金・レスポンス劣化を引き起こすOWASP「セキュリティ設定ミス」に相当し、安定運用に直結する。

**Independent Test**: 設定された上限を超えるサイズのTXTファイルを監視フォルダに置いて処理させ、処理スキップまたはレビューフォルダへ送られることを確認できる。

**Acceptance Scenarios**:

1. **Given** 設定ファイルに各ファイルタイプのサイズ上限が定義されている、**When** 上限を超えるファイルが監視フォルダに置かれる、**Then** 処理はスキップされ、ファイルはレビューフォルダへ移動され、スキップ理由が監査ログに記録される
2. **Given** 設定ファイルに各ファイルタイプのサイズ上限が定義されている、**When** 上限以下のファイルが投入される、**Then** 通常通り処理が実行される
3. **Given** サイズ上限の設定が存在しない（省略されている）、**When** システムが起動する、**Then** システムはデフォルト値（全ファイルタイプ共通の安全な上限）を適用し、警告ログを出力する

---

### User Story 3 - 機密情報を含む監査ログの保護 (Priority: P2)

`contractSubject`・`contractPeriod` などの機微情報が監査ログに記録される際、平文のまま保存されず、ログファイルへのアクセスが制限される。ログ管理者は、ログを閲覧しても機密情報が直接可読されない状態であることを確認できる。

**Why this priority**: 平文での機微情報記録は「機密データの露出（OWASP A02）」に該当し、ログファイルへの不正アクセス・誤配布時の情報漏洩リスクがある。

**Independent Test**: 契約情報を含むファイルを処理させ、生成された監査ログファイルに `contractSubject` の実値が平文で含まれていないことをテキスト検索で確認できる。

**Acceptance Scenarios**:

1. **Given** 機密フラグ付きのフィールド（`contractSubject` 等）が分類・抽出された、**When** 監査ログに書き込まれる、**Then** 当該フィールドはマスク（例：`[REDACTED]`）または省略された状態で記録される
2. **Given** ログディレクトリが存在する、**When** ログファイルが生成される、**Then** ログファイルのパーミッション設定により、プロセスオーナー以外の読み書きが制限される（OS が許す範囲で設定される）
3. **Given** 機密フラグのないフィールド（カテゴリ・タグ等）、**When** 監査ログに書き込まれる、**Then** 当該フィールドは通常通り記録され、ログの可読性・追跡性が損なわれない

---

### User Story 4 - ファイルタイプ検証による不正ファイルブロック (Priority: P2)

拡張子を偽装したファイル（例：`.txt` に改名したバイナリ）が監視フォルダに置かれた場合、システムはファイルの実際のコンテンツタイプを検証し、不一致のファイルを処理せずにスキップ・拒否する。

**Why this priority**: 拡張子偽装による不正ファイル処理はOWASP「安全でないデシリアライズ」および「インジェクション」に関連するリスク。コンテンツタイプ検証により、予期しないファイル形式による処理エラーや悪意のあるファイルのパイプライン通過を防ぐ。

**Independent Test**: `.txt` 拡張子に改名したバイナリファイルを監視フォルダに置き、システムが処理をスキップしてログに拒否理由を記録することを確認できる。

**Acceptance Scenarios**:

1. **Given** 拡張子が `.txt` のファイルだが実際のコンテンツがバイナリ、**When** 監視フォルダで検出される、**Then** システムはコンテンツタイプの不一致を検出し、処理をスキップして拒否理由を監査ログに記録する
2. **Given** 拡張子とコンテンツタイプが一致する正常なファイル、**When** 監視フォルダで検出される、**Then** 通常通り処理が実行される
3. **Given** 未対応のファイルタイプ（サポート外の MIME タイプ）、**When** 監視フォルダで検出される、**Then** 処理対象外としてスキップされ、監査ログに記録される

---

### Edge Cases

- `watchDir` と振り分け先が同じパスに設定された場合は起動時バリデーションエラーとしてプロセスを終了する（解決済み）
- 書き込み途中のファイルに対するサイズ検証は、`chokidar` の `awaitWriteFinish` オプションで書き込み完了待機後にキューへ积むことで対応する（解決済み）
- ログマスク対象フィールドの定義が変更された場合、過去ログへの影響はどうするか（過去ログは対象外とする）（Assumptions 参照、解決済み）
- 拡張子なしのファイルが投入された場合は処理拒否してレビューフォルダへ移動し、監査ログに「拡張子なし」として記録する（解決済み）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはファイルの移動・コピー操作を実行する前に、移動先パスが `watchDir`（および設定で許可されたルートディレクトリ）の配下であることを検証し、範囲外の場合は操作を中断しなければならない
- **FR-001b**: システムは設定読み込み時に `watchDir` と全振り分け先パスの一致（循環参照）を検証し、一致する場合はバリデーションエラーとしてプロセスを即時終了してエラーログに記録しなければならない
- **FR-002**: システムはファイルパスの正規化（`path.resolve()` による絶対パス変換および `../` シーケンスの解消・Nullバイト除去）を行い、正規化後のパスが許可された範囲内であることを確認しなければならない（シンボリックリンクの完全解決はスコープ外とし、`path.resolve()` ベースの正規化で対応する）
- **FR-003**: 設定ファイルはファイルタイプ（txt / md / pdf / docx / xlsx / png / jpg 等）ごとに個別のサイズ上限（MB単位）を定義できなければならない
- **FR-004**: システムはファイル処理開始前にファイルサイズを検査し、対応するタイプの上限を超えている場合は処理をスキップしてレビューフォルダへ移動し、監査ログにスキップ理由とファイルサイズを記録しなければならない
- **FR-005**: 設定ファイルにタイプ別のサイズ上限が定義されていない場合、システムはデフォルトのハード上限 **50MB**（全タイプ共通）を適用し、設定不備を警告ログとして出力しなければならない
- **FR-006**: 監査ログへの書き込み時、`config.json` の `sensitiveFields` 配列に列挙されたフィールド（例：`["contractSubject", "contractPeriod"]`）はマスク処理（`[REDACTED]`）を施してから記録しなければならない。`sensitiveFields` が未定義の場合はデフォルト値 `["contractSubject", "contractPeriod"]` を適用する
- **FR-007**: ログファイル生成時、OSの許可する範囲でファイルパーミッションを制限し、プロセスオーナー以外が読み書きできない設定を適用しなければならない
- **FR-008**: システムはファイルのMIMEタイプ（コンテンツ先頭バイトのマジックナンバー等）を検査し、拡張子とコンテンツタイプが一致しない場合は処理を拒否して監査ログに記録しなければならない。また、**拡張子が存在しないファイルは一律で処理拒否し、レビューフォルダへ移動して監査ログに拒否理由「拡張子なし」を記録しなければならない**
- **FR-009**: パス検証・サイズ検証・コンテンツタイプ検証はすべてパイプライン処理の最前段（キューから取り出した直後）で実行しなければならない
- **FR-010**: セキュリティ検証で拒否されたファイルはレビューフォルダへ移動し、元のファイルは削除・上書きしてはならない

### Key Entities

- **セキュリティバリデーション結果**: 検証種別（パス・サイズ・MIME）、判定結果（合格/拒否）、拒否理由、ファイルサイズ、検出されたMIMEタイプ
- **マスク対象フィールド定義**: フィールド名リスト、マスク文字列（デフォルト：`[REDACTED]`）
- **ファイルタイプ別サイズ設定**: 拡張子またはMIMEタイプ、上限サイズ（MB）、デフォルト上限（50MB）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `watchDir` の外を指す振り分け先パスが設定された状態で100件のファイルを処理しても、一件も `watchDir` 外へ移動されない（100%ブロック率）
- **SC-002**: 設定されたサイズ上限を超える全ファイルが処理スキップされ、監査ログに記録される（漏れ率0%）
- **SC-003**: 機密フィールドを含む監査ログを生成した後、ログファイルをテキスト検索しても機密値（契約対象名・期間値）が平文で発見されない
- **SC-004**: 拡張子偽装ファイル（テスト用バイナリを `.txt` に改名）を投入した場合、100%の割合でコンテンツタイプ不一致として拒否される
- **SC-005**: セキュリティ検証処理による正常ファイルの追加処理時間が、従来の処理時間の10%以内に収まる（パフォーマンス影響の最小化）
- **SC-006**: 全セキュリティ検証ロジックにユニットテストが存在し、テストカバレッジが90%以上を維持する

## Clarifications

### Session 2026-06-01

- Q: 機密フィールドの設定場所はどこか？ → A: `config.json` に専用配列 `sensitiveFields` を追加する（コード変更なしに変更可能）
- Q: 全ファイルタイプ共通のデフォルトサイズ上限は何MBか？ → A: 50MB（タイプ別設定がない場合のフォールバック値）
- Q: 拡張子なしのファイルが投入された場合の挙動は？ → A: 処理拒否してレビューフォルダへ移動し、監査ログに記録する
- Q: `watchDir` と振り分け先が同じパスの場合（循環参照）はどう扱うか？ → A: 起動時バリデーションエラーとしてプロセスを終了し、エラーログに記録する
- Q: 書き込み途中のファイルに対してサイズ検証が実行された場合の挙動は？ → A: `chokidar` の書き込み完了待機（awaitWriteFinish）後にサイズ検証を実行する

## Assumptions

- ウイルス/マルウェアスキャンは本スペックのスコープ外とする（外部スキャンエンジン連携は別フェーズで検討）
- ログの暗号化（保存時暗号化）はOSレベルの対応（BitLocker等）で担保することを前提とし、アプリケーション層では機密フィールドのマスクとパーミッション設定に留める
- MIMEタイプ検証はファイルの先頭バイト（マジックナンバー）による判定を基本とし、外部のウイルス対策ソフトとの連携は行わない
- `watchDir` は設定ファイルで静的に定義され、ランタイムに変更されないことを前提とする
- 既存の監査ログファイル（過去ログ）の遡及マスクは対象外とし、本機能導入後に生成されたログのみを対象とする
- WindowsおよびmacOS/Linux環境でのパス正規化処理の差異はプラットフォーム標準ライブラリで吸収する
- ファイル監視には `chokidar` の `awaitWriteFinish` オプションを有効にし、書き込み完了後にのみキューへ積む設計とする（書き込み途中ファイルはキューに入らない）
