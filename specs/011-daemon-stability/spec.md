# Feature Specification: デーモン安定性・信頼性強化

**Feature Branch**: `011-daemon-stability`

**Created**: 2026-06-01

**Status**: Complete (実装完了 2026-06-03)

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 長時間稼働でメモリが増え続けない (Priority: P1)

システム管理者が JudgeFile デーモンを数週間・数ヶ月にわたって無停止で稼働させるとき、処理済みファイルの重複排除に使う内部テーブルがメモリを際限なく消費することなく、安定した使用量を保つ。

**Why this priority**: メモリリークはサービス継続性に直接影響し、OOM によるプロセス強制終了を引き起こす最も高リスクな問題。

**Independent Test**: デーモンを起動し、10,000 件を超えるファイルを順次投入したとき、プロセスのメモリ使用量が一定の上限内に収まることを確認できる。

**Acceptance Scenarios**:

1. **Given** 重複排除テーブルがエントリ上限（10,000 件）に達している状態で、**When** 新しいファイルが検知されたとき、**Then** 最も古いエントリが削除されてから新しいエントリが追加され、テーブルサイズが上限を超えない。
2. **Given** デーモンが長時間稼働している状態で、**When** 大量のファイルが処理されたとき、**Then** 重複排除テーブルのエントリ数が設定上限（デフォルト 10,000）を超えない。
3. **Given** 重複排除テーブルの上限が未設定の場合、**When** デーモンが起動したとき、**Then** デフォルト値（10,000）が使用される。

### User Story 2 — SIGTERM/SIGINT で処理を安全に完了してから終了する (Priority: P1)

運用担当者がデプロイ更新や計画停止のため `kill` コマンドまたはコンテナオーケストレータのシャットダウンシグナルを送ったとき、処理中のファイルがすべて完了（または明示的にロールバック）してからプロセスが終了し、ファイルが中途半端な状態で残らない。

**Why this priority**: ファイル移動中断はデータ破損（移動元にも移動先にも存在しない状態）を引き起こすため、メモリリークと同等の優先度。

**Independent Test**: デーモンが複数のファイルを並列処理中に SIGTERM を送信したとき、すべての処理中ジョブが正常終了または `reviewDir` に安全に保存されてからプロセスが終了することを確認できる。

**Acceptance Scenarios**:

1. **Given** デーモンがファイルを並列処理している状態で、**When** SIGTERM を受信したとき、**Then** 新たなファイル検知を停止し、処理中ジョブがすべて完了してからプロセスが終了する。
2. **Given** デーモンが SIGTERM を受信した状態で、**When** 処理完了まで 30 秒以上かかりそうな場合、**Then** タイムアウト後に残存ジョブを `reviewDir` に移動し、タイムアウト終了をログに記録してプロセスを終了する。
3. **Given** SIGINT（Ctrl+C）を受信したとき、**Then** SIGTERM と同じグレースフル停止フローが実行される。
4. **Given** グレースフル停止中に新たなファイルが監視フォルダに置かれたとき、**Then** そのファイルはキューに追加されず無視される。

### User Story 3 — ファイル移動が同名ファイルを上書きしない (Priority: P2)

複数ファイルが同時にキューで処理されるとき、移動先の同名ファイルの存在確認から実際の移動完了までの間に別のプロセスが同名ファイルを書き込んでも、どちらのファイルも失われない。

**Why this priority**: データロストは復元不可能な被害であり、マルチプロセス環境や高負荷時に発生リスクがある。

**Independent Test**: 同じ名前のファイルを同時に 2 件処理したとき、両ファイルが別々のパス（例: `document.pdf` と `document-{suffix}.pdf`）として移動先に保存されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 移動先に同名ファイルが存在する状態で、**When** `resolveDestination` が呼ばれたとき、**Then** UUID または十分な一意性を持つサフィックスを含む衝突しないファイル名が返される。
2. **Given** 2 つのジョブが同じ宛先パスを同時に解決しようとしているとき、**Then** 一方は衝突を検知してサフィックス付きパスを使用し、どちらのファイルも失われない。

---

### User Story 4 — 再起動後に処理済みファイルが再処理されない (Priority: P2)

デーモンを再起動した直後に監視フォルダに以前処理済みのファイルが残っていても、それらが再度キューに投入されて重複処理されない。

**Why this priority**: 再起動のたびに重複処理が発生すると、ファイルの多重移動・重複ログ・AI API の無駄呼び出しが生じる。

**Independent Test**: ファイルを処理してデーモンを再起動し、同じファイルが監視フォルダに残っている状態で `ignoreInitial: false` 相当の設定を使ったとき、重複処理が発生しないことを確認できる。

**Acceptance Scenarios**:

1. **Given** ファイルが正常に処理され、デーモンが停止した状態で、**When** デーモンを再起動したとき、**Then** 処理済みファイルの記録がディスクから読み込まれ、同一ファイルがキューに積まれない。
2. **Given** 処理済みファイルの記録ファイルが壊れているまたは存在しないとき、**When** デーモンが起動したとき、**Then** エラーで停止せず、空の状態から通常起動する。
3. **Given** 処理済みファイルとして記録されたファイルが後から内容変更された場合（ファイルサイズや更新日時が変わった場合）、**When** デーモンが再起動したとき、**Then** 変更後のファイルは新規ファイルとしてキューに積まれる。

---

### User Story 5 — 外部監視ツールがデーモンの稼働状態を確認できる (Priority: P3)

インフラ担当者が Prometheus、Docker ヘルスチェック、または独自の監視スクリプトからデーモンの稼働状態・キュー状況をポーリングしたとき、正常稼働中は HTTP 200 を、異常時は HTTP 503 を返す。

**Why this priority**: 単体デーモンとして動作する現フェーズでは stdio ログで運用可能であり、将来の SaaS 化・コンテナ対応時に重要度が増す。

**Independent Test**: デーモンを起動した状態で `GET /health` を呼ぶと `{"status":"ok"}` が返り、デーモンを停止した状態では接続が失敗することを確認できる。

**Acceptance Scenarios**:

1. **Given** デーモンが正常稼働中のとき、**When** `GET /health` を呼んだとき、**Then** HTTP 200 と `{"status":"ok","queueSize":<n>,"uptime":<秒>}` が返される。
2. **Given** デーモンがシャットダウン中のとき、**When** `GET /health` を呼んだとき、**Then** HTTP 503 が返される。
3. **Given** ヘルスチェックポートが設定ファイルで未指定のとき、**When** デーモンが起動したとき、**Then** ヘルスチェックサーバーは起動しない（オプトイン）。

---

### User Story 6 — 人間の修正記録が改ざんされても検知できる (Priority: P3)

コンプライアンス担当者が `corrections.jsonl`（人間レビューによる修正ログ）を監査するとき、記録が後から改ざんされていないことを確認できる。

**Why this priority**: 監査ログ（`audit-*.jsonl`）と同じ保護水準を修正記録にも適用することで、監査証跡の完全性を担保する。

**Independent Test**: `corrections.jsonl` に HMAC 保護を有効にした状態でレビュー CLIを実行し、その後ファイルを手動で改ざんしてから検証ツールを実行したとき、改ざんが検知されることを確認できる。

**Acceptance Scenarios**:

1. **Given** レビュー CLI でファイルを承認・修正したとき、**Then** `corrections.jsonl` に記録されるエントリに `prevHash`/`currHash` が付与される（AUDIT_HMAC_SECRET が設定されている場合）。
2. **Given** `corrections.jsonl` のエントリが改ざんされた状態で、**When** `verify-log.ts` で検証したとき、**Then** 改ざん箇所が違反として報告される。
3. **Given** AUDIT_HMAC_SECRET が未設定のとき、**When** レビュー CLI が修正を記録したとき、**Then** HMAC なしで記録され、警告を標準エラーに出力する。

---

### Edge Cases

- `seenKeys` の上限に達したタイミングで削除対象と同じキーの新ファイルが来た場合の扱い（削除→再登録で正しく処理される）
- グレースフル停止タイムアウト中にプロセスが `SIGKILL` を受けた場合（ファイル移動の中断はやむを得ず `reviewDir` に残す）
- 処理済みファイル記録（永続化ファイル）が書き込み権限なしの場合の起動挙動（ログ警告を出して in-memory 運用にフォールバック）
- `resolveDestination` でサフィックス衝突が連続して発生した場合（UUID を使うため実用上衝突しない）
- ヘルスチェックポートが使用中の場合（エラーログを出力してプロセスを終了する）（FR-007、Clarifications Q5 参照）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは `seenKeys` テーブルのエントリ数に設定可能な上限（デフォルト 10,000）を設け、上限に達した場合は最も古いエントリを削除してから新しいエントリを追加しなければならない
- **FR-002**: システムは SIGTERM / SIGINT を受信したとき、新規ファイルの監視を停止し、処理中のすべてのキュージョブが完了するまで待機してからプロセスを終了しなければならない
- **FR-003**: グレースフル停止のタイムアウト（設定可能、デフォルト 30 秒）を超えた場合、システムは処理中断ファイルを `reviewDir` に移動し、`event: 'stopped'` および中断理由を監査ログに記録した上でプロセスを終了しなければならない
- **FR-004**: `resolveDestination` は移動先に同名ファイルが存在する場合、UUID ベースのサフィックスを使って衝突しない一意なパスを返さなければならない
- **FR-005**: システムは処理済みファイルの識別キー（ファイル名・サイズ・mtime の組み合わせ）を `completed` イベント記録後にディスク上に永続化し、再起動後に読み込まなければならない。`failed` イベントのファイルは永続化しない（再試行可能にするため）。ファイル形式は 1 行 1 キー文字列（`"filename:size:mtimeMs"`）のプレーンテキストとする
- **FR-006**: 処理済みファイル記録の永続化ファイルが存在しないまたは破損している場合、システムはエラーで停止せず空の状態で起動しなければならない
- **FR-007**: `config.json` に `healthCheck.port` が指定されている場合、システムはその TCP ポートで HTTP ヘルスチェックサーバーを起動しなければならない。ポートが使用中の場合はエラーログを出力してプロセスを終了する（監視システムによる再起動を期待する）
- **FR-008**: ヘルスチェックエンドポイント `GET /health` は `{"status":"ok"|"shutting_down","queueSize":<n>,"uptime":<秒>}` を返さなければならない
- **FR-009**: `AUDIT_HMAC_SECRET` が設定されている場合、レビュー CLI は `corrections.jsonl` に書き込む各エントリに `prevHash`/`currHash` を付与しなければならない
- **FR-010**: `corrections.jsonl` は `config.json` の `correctionsFile` キーで指定したパスに出力し、既存の `verify-log.ts --file <path>` で HMAC 検証可能な形式で記録されなければならない
- **FR-011**: `src/types/index.ts` の `AuditEvent` 型に `'stopped'` を追加し、タイムアウト中断ログで使用しなければならない

### Key Entities

- **SeenKeyStore**: 処理済みファイルキーの集合。最大エントリ数を持ち、上限超過時は最古エントリを削除する。永続化ファイル（プレーンテキスト、1 行 1 キー）への読み書きを行う
- **HealthCheckServer**: HTTP サーバー（オプション）。キューサイズ・稼働時間・シャットダウン状態を公開する
- **GracefulShutdown**: SIGTERM/SIGINT ハンドラ。監視停止→キュー完了待機→ヘルスチェック停止→プロセス終了のシーケンスを管理する

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 10,000 件以上のファイルを連続処理してもプロセスのメモリ使用量が起動直後から 200MB 以上増加しない
- **SC-002**: SIGTERM 受信から最後のキュージョブ完了まで、処理中のファイルがどれも失われない（処理済みまたは `reviewDir` に保存）
- **SC-003**: 同じファイル名を持つ 2 件のファイルを同時処理したとき、移動先で 1 件も上書きされず 2 件とも別パスに保存される
- **SC-004**: デーモン再起動後、起動前に処理済みとして記録されたファイルに対して重複処理イベントが発生しない
- **SC-005**: `GET /health` のレスポンスタイムが 100ms 未満（ヘルスチェック機能有効時）
- **SC-006**: `corrections.jsonl` への不正な変更が `verify-log.ts` で 100% 検知される

---

## Assumptions

- `seenKeys` の永続化ファイルは `config.json` の `logFile` と同じディレクトリに `seen-keys.jsonl` として保存する
- グレースフルシャットダウンのタイムアウトデフォルト値は 30 秒とする
- ヘルスチェックサーバーはオプション機能（`config.json` の `healthCheck.port` で有効化）とし、未設定時は起動しない
- `corrections.jsonl` の HMAC 保護は `AUDIT_HMAC_SECRET` が設定されている場合のみ有効になる（監査ログと同じシークレットを共用）
- `seenKeys` の上限はデフォルト 10,000 件とし、`config.json` で変更可能とする
- 処理済みファイル記録の LRU 削除は「追加順」（挿入順 Set）で行う
